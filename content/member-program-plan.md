# 潮旅國際｜澎湖百旅計畫 — 會員制度實作工單

> 依 2026-08-19 的會員制度規劃整理成可交辦工單。
> 原則：**嵌入既有網站**，不另建獨立會員站；會員資訊出現在首頁、行程卡、行程頁、諮詢表單、LINE，而不是單一靜態說明頁。
> **鐵則：所有前台文案一律五國語言（繁中/en/ja/ko/zh-cn），流程見 skill `phbay-i18n`。**

主標語：**一百次來澎湖，每一次都有新的風景。**
會員專頁網址：`/penghu-100`

## 0. 與現有系統的對接評估（動工前先讀）

現有可直接沿用的基礎：

| 現有資產 | 可如何用於會員制度 |
|---|---|
| `contacts` 表＋線上諮詢表單 | 加兩個欄位即可蒐集會員編號與旅次自述，成本最低、最先做 |
| `neihai_preorders` / `preorders` 表 | 訂單完成後認列旅次的來源；已有後台編輯與修改紀錄 |
| 後台 `/admin` 三角色分權（owner/orders/editor） | 會員管理需新增第四種角色或掛在 orders 下 |
| LINE Messaging API（webhook 已上線，`line_users` 表已記錄 userId） | 會員綁定與升等通知的現成管道，不必另開發 |
| `pillar_pages.py` 伺服器渲染架構 | `/penghu-100` 直接用同一套，順便吃到 SEO |
| `i18n.js` / `faq-i18n.js` 五語字典 | 會員文案沿用同一機制 |

**已知風險與限制**

1. **個資法**：會員要蒐集姓名、手機、生日、LINE UID，屬個人資料。專案已有個資告知與同意的既有做法（內海預購頁），會員註冊必須比照辦理：告知蒐集目的／期間／方式／權利＋必勾同意。另注意目前 DB 對身分證是明文儲存（既有待強化項），會員資料不應再擴大明文敏感欄位範圍——**生日建議只存月份或設定為選填**，避免蒐集超出必要。
2. **代售行程佔多數**：目前約 57 筆行程中，47 筆是公會會員與主題遊程徵選的**代售產品**，由其他旅行社執行。在這些卡片上顯示「完成可累積潮旅點數」會誤導旅客——**需先界定哪些行程可認列旅次**（見下方待決事項）。
3. **旅次認定**：規劃已正確指出應依「已完成旅程」而非下單計算。實作上需要在訂單資料加「是否計入旅次」與「完成狀態」欄位，並由客服人工確認（第一階段）。

### P0-5 LINE 作為第一階段日常入口
- [ ] 註冊完成後導引加入官方帳號並綁定（沿用既有 webhook 記錄 userId 的機制）。

## ⚠️ 待使用者決定（這些沒定案，程式無法動工）

1. **旅次認列範圍**：只算潮旅自營行程？潮旅經手報名的代售行程也算？還是憑證明都算？
2. **點數價值與兌換**：1 次旅程 100 點，那 100 點能換什麼、折抵多少錢？點數會過期嗎？（涉及實際成本，需老闆定價）
3. **會員編號規則**：例如 `PH-2026-0001`，或沿用手機號碼？
4. **生日欄位**：是否必填？建議只收月份（生日禮用）以降低個資風險。
5. **福利內容定案**：四類福利中每一項的實際內容與成本（例如「行程升級禮遇」具體是什麼）。
6. **等級門檻**：100 次是品牌理念，實務上 30／50／100 次幾乎不會有人達成——是否改為「旅次＋點數」雙軌，或把高階等級當成榮譽象徵即可？
